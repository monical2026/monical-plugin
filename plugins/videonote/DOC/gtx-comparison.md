# client=gtx 与本地翻译对照试验

## 本轮结论

2026-09-11，用户明确授权对先前同一组 8 条英文样本调用 client=gtx 做对照。此次请求未取得译文，因此不能判定 gtx 比本地更好或更差，不切换默认引擎。

## 方法和实际结果

- 样本：与 [本地翻译评估](local-translation-evaluation.md) 相同的 8 条人工编写英文，保持完整句段，不含私人笔记和凭据。
- 目标：translate.googleapis.com/translate_a/single；参数 client=gtx、sl=en、tl=zh-CN、dt=t。每条样本分别请求。
- 初次 Node 直连出现 fetch failed；单独 curl 连接检查超时。停止直连批次后检查系统代理配置，发现终端没有自动使用 macOS 已配置的代理。
- 通过当前系统代理执行后，T01–T08 均返回 HTTP 429，没有翻译正文。HTTP 429 按限流/访问受限处理；未确认是出口共享限额、端点规则还是中间网络策略，不将猜测作为根因。
- Ego Lite 尝试访问后仍停留在 about:blank，没有取得可用响应；不把空白页当作质量结果。
- 第一版脚本在每条失败后继续下一个样本，导致同一轮 8 条均受到限制。已调整：遇到 429 或 403 立即停止本轮，并记录 Retry-After；没有为验证该改动继续请求线上端点。
- 未切换出口、未换地址绕过限制、未调用云端 LLM；未改变产品翻译引擎配置。

## 用户反馈后的结论修正

用户报告同一类 client=gtx 通道刚刚能够成功翻译。此前测试只证明本脚本、所用主机和当前网络路径收到 HTTP 429，不能外推为该通道不可用或不稳定。双方实际完整端点、调用环境与请求方式尚未对齐。

旧探针只保留状态码，没有记录足以确认响应来源的响应元数据，无法区分端点限制与中间网络策略。不得将这次失败当作两种引擎的可用性比较结论。修复停止批次逻辑不等于修复连接问题。

速度尚无成对实测。本地 70 ms 为模型准备完成后、8 个短句段的循环耗时；不含字幕获取、首次准备、整片任务调度，不能外推到一小时视频。gtx 没有成功译文耗时，不能计算速度差或倍数。

后续对照须使用相同完整文字与句段边界，分别测首段出现时间和全文完成时间；本地分首次准备与热态，云端包括请求往返；缓存命中另列，不能与首次翻译混比。真实长逐字稿另测，记录分批、并发和失败情况。用户成功请求的端点与环境确认后再做有针对性的复现，不盲目密集重试。
